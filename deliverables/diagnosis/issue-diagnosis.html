ISSUE-001

空格 PDF 召回失败：CJK 字体渲染给拉丁字符插空格

语料 / 嵌入
问题现象

16 题 × 3 配置 = 48 个样本 Context Precision 全部为 0，占 CP 损失 50.8%。

日志证据

# R6 在册异常 #1（eval-history）
"空格 PDF 召回失败（16 题×3 配置 CP=0，占 CP 损失 50.8%）"
# 语料产物抽查：拉丁字符间被插入空格
"compliance-guide.en.md" 渲染后 "g i f t   r e g i s t e r"

根因分析

转 PDF 时沿用演示语料生成器的 CJK 字体缺陷：china-s 字体渲染拉丁字符时在字符间插入空格，导致 BGE-M3 对英文条款的嵌入彻底失效——向量检索对这批 chunk 的相似度归零，召回失败。

修复方案

  • F1 块级双字体渲染：中文用 CJK 字体、拉丁用拉丁字体，生成器与语料 PDF 同步修复重灌。
修复前 CP0.6558 / 0.6440 / 0.6624 → 修复后 CP0.7694 / 0.7563 / 0.7697
三配置 +10.7% / +11.2% / +11.4%

ISSUE-002

Compliance 恒 5：judge 思考链吃满 max_tokens

指标失真
问题现象

切换 deepseek-v4-flash 后，Answer Compliance 三配置恒 ≈1.0（judge 恒打 5 分），指标失去区分度，无法反映真实合规质量。

日志证据

# eval/runner.py _judge_llm_call 注释原文
"deepseek-v4-flash 默认开启思考模式：思考链（reasoning_content）
 会吃满 max_tokens=100，导致 content 恒空 → judge_unparsable"
[2026-08-15 17:41:12Z] warning judge_unparsable content="分数|理由" (eval.runner)

根因分析

v4-flash 默认开启思考模式，思考链（reasoning_content）先占用生成预算。judge 请求 max_tokens=100 本意是限制输出长度，预算却被思考链吃满，content 退化（恒打 5 分或输出模板字面量）。Ragas judge（faithfulness/CP）同样受影响——长 prompt 推理极慢，实测 4 分钟仅完成 27%。

修复方案

  • 对 judge / generator / Ragas 三处统一显式关闭思考模式 thinking: {"type": "disabled"}。
  • judge 是"分数|理由"裁决，无需思考链；关闭后行为对齐旧 deepseek-chat。
修复前 Compliance恒 1.0（假象） → 修复后 Compliance0.9067 / 0.9465 / 0.9070
指标恢复真实区分度，跨模型稳定达标 ≥0.80
ISSUE-003

hybrid+rerank 过度拒答：全文 rerank 超时 → 空检索 → 误拒

指标失真
问题现象

hybrid+rerank 配置对正常业务问题过度拒答，实测 45 条误拒；R7 该配置 Refusal 仅 0.8545（三配置最低）。

日志证据

[2026-08-15 15:51:32] warning stage_timeout stage=retrieval timeout=5
[2026-08-15 15:51:32] warning retrieval_stage_timeout query="员工每年带薪病假的上限是多少天？"
[2026-08-15 15:51:32] info retrieval_complete mode=hybrid+rerank final_chunks=0 latency_ms=5001
[2026-08-15 17:39:24] info refusal_triggered reason=low_confidence signal=0.3862 (chat)

根因分析

全文 rerank 30 候选实测 ~5s；eval 并发 5 在 MPS 上争抢，排队的粗排 retrieval 要等前面的 rerank 释放 GPU 才轮到，粗排阶段超时（5s）→ coarse_candidates=0 → 空 sources → RefusalCheck 规则 1 判 low_confidence。语义错误：把"没来得及搜"（超时）与"查无信息"（检索为空）归入同一条空结果规则。

修复方案

  • rerank 输入截断 input_truncate_chars=300（全文 ~5s → ~1.5s）。
  • retrieval.timeout 5s → 7s（给排队检索留余量）。
  • 超时语义区分：检索超时返回"系统繁忙"降级话术，Refusal 计算排除超时样本。
修复前 Refusal0.8545 → 修复后 Refusal0.9909
+13.6pp（相对 +16.0%），误拒 45 → 14，阶段超时 19/12/8 → 0/0/0
ISSUE-004

OOS 漏拒：top1_sim 阈值区分不了"话题相似 OOS"

拒答口径
问题现象

部分 OOS 样本未拒答，LLM 直接编造答案。R6 OOS 拒答率三配置仅 0.17 / 0.22 / 0.83；修复后 R9 三配置统一 1.0。

日志证据

# R6 在册异常 #4（eval-history）
"38 个 OOS 样本 refused=False 漏过过滤，compliance -0.10"
# postprocess.py RefusalCheck 规则 2：仅 top1_sim < 0.45 判拒
"公司打印机卡纸怎么修" 类话题相似 OOS 实测 sim=0.59 > 0.45 → 漏过

根因分析

两层根因叠加：① 置信度阈值只认"向量相似度低"，但话题相似 OOS（公司内部设备维修/IT 类）与政策文档同域，top1_sim 天然偏高（0.59 > 0.45），规则 2 无法拦截；② 大语料下检索不再为空，规则 1（空结果→拒答）失效。

修复方案

  • 安全/PII 关键词扩展（入侵/挖矿/防火墙/年薪/工资/Wi-Fi 密码，不含会误伤政策题的"密码"）。
  • 注入检测前置：detect_injection(query) 最先判 safety。
  • OOS 软拒 judge：对 refused=False 的 OOS 样本，用 LLM judge 区分"软拒答"与"编造答案"。
修复前 OOS 拒答率0.7222 → 修复后 OOS 拒答率1.0
+27.8pp（相对 +38.5%），三配置统一 1.0
